OPUS Container Wiki — the unofficial CyberLogitec reference

CyberLogitec OPUS Container (sometimes also referred to as LMS, Allegro, or just "the Cyberlogitec system") is the enterprise shipping suite used by your company to run container operations — from creating a booking, issuing a service order, auditing vendor invoices, posting the settlement to the ERP, through to performance analysis and profitability reporting.

This wiki consolidates the five main OPUS Container user manuals into a single, searchable reference written from the perspective of a cost / finance user. It explains what each screen is for, what to put in each field, how the UI interprets your input, and how the modules tie together at the end of the month.

What is OPUS / LMS / Allegro?

OPUS Container is a modular, browser-based liner-shipping suite built by CyberLogitec. It covers the full container-carrier business cycle: commercial (rates, booking, B/L), operations (vessels, terminals, equipment), logistics (inland transport), and finance (accrual, settlement, invoice, interface to ERP).

You may hear the system called three different names inside your company — they refer to the same family but not always to the same thing:

OPUS Container
The official CyberLogitec product name. All of the user manuals you've been given are titled OPUS Container User Manual – [Module].
LMS
"Logistics Management System." At your company this is the internal nickname for the transport / logistics-cost side of OPUS — essentially the PSO, TES and TRS modules plus their agreement & invoice screens. The companion LMS User Guide PDFs are written by your company's rollout team, not by CyberLogitec, and describe your company's actual configuration (office codes, cost-code mapping, approval routing).
Allegro
Historically CyberLogitec named an earlier generation of the product "ALLEGRO". Many liner companies still call the whole suite "Allegro" out of habit even after it was rebranded OPUS. If someone says "check Allegro" they almost certainly mean "log into OPUS".

Who does what in OPUS — a Cost Controller's mental model

Think of OPUS as a pipeline, not a single application. Each module owns one stage of the lifecycle and hands data to the next one. A useful mental model:

  1. Sales sells a slot — creates a BKG.
  2. COA accrues the cost of that BKG in real time using unit-cost tables you maintain.
  3. Operations runs the move — the vessel sails (VSK), containers are handled at the terminal (TES), trucked inland (TRS), ports are called (PSO), slots are swapped with partners (JOO).
  4. Vendors send invoices. You audit them in TES / TRS / PSO.
  5. Each confirmed invoice becomes a CSR that lands in the ERP as an A/P voucher.
  6. COA recalculates the booking cost against actuals and drives the profitability reports.

Most of the complaints you'll hear ("why doesn't my accrual match actual?", "why is this booking red?", "why is CSR stuck?") are about breakages at one of those handoffs — and the troubleshooting pattern is always the same: trace the data back one module at a time.

OPUS uses a classic three-level menu structure. Every screen in the manuals is introduced with a Navigation: path of the form:

Sales Management > CNTR BIZ PFMC Analysis > Cost Table > Set-Up C/A Code > Register C/A Code

Read left-to-right this is:

  1. Top-level menu (Sales Management, Service Management, Vessel Operation, Trade Management, etc.) — the big horizontal tabs or top bar in OPUS.
  2. Module name (CNTR BIZ PFMC Analysis = COA, TML INV = TES, Port Service Order = PSO, Joint Operation = JOO, Transportation Service = TRS). This is the second-level menu within the module group.
  3. Function group (Cost Table, Invoice, Agreement, CSR Creation, Report…).
  4. Screen (Register C/A Code, MR Invoice Creation & Correction, Port Tariff Creation…). This is what actually opens as a tab.

Tabs stay open

OPUS opens each screen as a tab inside the workspace. You can have a dozen screens open at once — useful when, for example, you want to keep the Port Tariff Inquiry open while creating the Port Charge Invoice. Unsaved changes in a tab are not preserved if you navigate away by clicking a menu link. Always Save before switching screens.

Office scope — why you can't see some data

Every user account is tied to one or more Offices in MDA. Inquiries and reports are filtered by the user's office scope. If a booking, invoice, or CSR "is missing", two causes dominate:

  • You are looking outside your office's scope. Either broaden the Office filter on the screen or request additional office access.
  • The transaction is saved under a Loading office different from your Contract office — see Office View (Contract vs Loading) in the COA article.

Common UI patterns across all modules

Home › Getting Started

Once you have used one OPUS screen you have seen them all. Every screen is a combination of three standard blocks. Recognising them turns any unfamiliar screen into one you can work with.

1. The header / filter block

Top of the screen. Fields with yellow (mandatory) or white (optional) backgrounds, plus a Retrieve button. Typical fields you'll see here:

Office
Always defaults to your logged-in office. Change it only if you have cross-office authority.
VVD (Vessel/Voyage/Direction)
Three-part key that identifies a specific voyage leg. Example: HMMA 2604E = vessel HMMA, voyage 2604, direction E (eastbound). Virtually every ops/cost screen uses VVD.
Period
From / To dates. Retrieval window — keep this narrow (≤ 1 month) on heavy inquiries to avoid timeouts.
Service Provider (S/P)
Vendor code from MDA. Has a magnifier lookup — you can search by name.
Status
Dropdown — e.g. Open / Confirm / Cancel, or Save / Approved / Rejected.

2. The main data grid

A spreadsheet-style grid below the filter. OPUS grids behave the same way everywhere:

  • Del column on the far left — tick it and Save to delete the row.
  • STS column — shows Ins (new row you are about to save), Upd (row you changed), or blank (unchanged).
  • Mandatory columns marked with a small ✓ in the header. You will get a save error if any are empty.
  • LOV columns — double-click the cell to open a lookup popup.
  • Sortable headers — click a column header to sort.
  • Row Add button below the grid to append a new row.
  • Down Excel / Up Excel — the primary way you move data in and out of OPUS. See the tip below.
Tip — always use Down Excel first. Before editing a grid with more than a handful of rows, export (Down Excel), edit in Excel, then re-upload (Up Excel). It is faster and gives you an auditable backup of your change. The upload validates every row before committing.

3. Tabs within the screen

Many cost screens use tabs to separate what matched from what didn't when you audit an invoice. The convention is:

Tab nameMeaning
CoincidenceContainer records that matched the agreement/rate successfully. These will become the paid amount if you confirm.
DiscrepancyContainer records that didn't match — wrong size, wrong date, no agreement loaded, etc. Needs your attention.
Cost Calc. / Cost CalculationThe rolled-up amounts by cost item. This is what posts to the ERP.
Cost Calc. (SR by FD / FP)Storage Revenue by Free Day / by Free Pool — two different storage-fee calculation methods that coexist because different depots use different free-day schemes.

A complete audit means the Discrepancy tab is empty (or only contains rows you've manually justified) and the Cost Calc totals match the vendor invoice within your tolerance.

Save → Confirm → Interface

Every transactional screen in OPUS moves through three states, in this order:

  1. Save — your edits are stored but nothing is posted. You can still edit / delete.
  2. Confirm — the document is locked. It's now ready to become a CSR. Edits are blocked; you have to Cancel Confirm first, if the screen allows.
  3. Interface (via CSR Creation) — the document is sent to the ERP's AP queue. After this, corrections require an ERP-side reversal.

When in doubt, Save freely, Confirm cautiously, and Interface only after month-end checks.

Watch out: OPUS will happily let you Confirm an invoice with a Discrepancy tab full of unresolved rows — those rows simply won't be billed. Always check the Discrepancy tab count is zero (or equals the rows you intentionally excluded) before pressing Confirm.

Core concepts & acronyms

Home › Getting Started

OPUS is dense with three-letter acronyms. This section is the cheat-sheet you'll refer to for the rest of your life with this system. See also the full Glossary.

VVD — Vessel / Voyage / Direction

The fundamental key in liner shipping. One VVD = one leg of one vessel's one voyage in one direction. Example: MSCX 2612W is vessel MSCX, voyage number 2612, westbound. A vessel's round trip has two VVDs (one each direction); some pendulum / multi-leg strings create more.

Virtually every operational cost in OPUS attaches to a VVD — port charges in PSO, slot settlement in JOO, allocation basis in COA.

BKG — Booking

The commercial contract for a shipment. One BKG covers one cargo movement, can be multi-container, multi-leg. In COA, every CM (Contribution Margin) calculation is per BKG — you accrue cargo-variable cost and recognise revenue at BKG level.

B/L — Bill of Lading

Issued at loading port. Locks the commercial terms and triggers the demurrage / detention clock. In liner cost terms, B/L is where the "revenue" number becomes firm and DEM/DET becomes calculable.

CSR — Consultation Slip Request

The OPUS-internal voucher that requests a posting in the ERP. Each confirmed invoice in TES / TRS / PSO / JOO produces a CSR. The CSR has:

  • A/P CSR — you owe the vendor (a payable).
  • A/R CSR — the partner owes you (a receivable). Common in JOO when your slot is underutilised by the partner.
  • CSR Approval step — an approver signs off inside OPUS before it interfaces.
  • CSR I/F Inquiry — shows whether the ERP accepted it.

Anything that is "not closed" at month-end almost always traces back to a CSR in Saved but not Approved state.

CM vs OP — Contribution Margin vs Operating Profit

Two profitability layers that COA calculates:

LevelRevenue capturedCosts deductedUnit of analysis
CM (Contribution Margin)Freight + miscellaneous per BKGCargo-variable costs (THC, inland, documentation, DG surcharge, etc.)Per BKG — answers "is this booking worth taking?"
OP (Operating Profit)Revenue at VVD levelCM costs + operation-variable (bunker, port charge, canal) + operation-fixed (EQ holding, general expenses)Per VVD — answers "did this voyage cover its run-cost?"

BSA — Basic Slot Allocation

When you share a service with alliance partners, each carrier is contractually entitled to a fixed number of slots (TEU) on each VVD. BSA defines those entitlements. JOO settles:

  • Slot Hire = your BSA × slot price (you pay for your allocation whether you use it or not).
  • OUS — Over-Used Slot = slots used above BSA, settled retroactively using TDR (Terminal Departure Report) or RDR (Regional Departure Report).
  • Surcharges — Reefer, DG (dangerous goods), Tank — extra charges for those specific container types.

TDR / RDR

TDR — Terminal Departure Report
Per-terminal container load report produced after each vessel departs. Used to calculate actual slot usage by carrier.
RDR — Regional Departure Report
Aggregated at region (e.g. Asia, Europe) level. Used when the settlement agreement is by region, not by terminal.

C/A Code — Chart of Account Code

The OPUS cost hierarchy is different from the ERP's GL accounts. COA maintains its own cost codes with three layers (Main Group → Sub Group → C/A Code → Cost Item) and a mapping to "SO Cost Code" (used by TES/TRS) and "Financial Cost Code" (used by PSO and the ERP). Maintaining this mapping correctly is the single most important thing you do for accrual-to-actual tie-out.

U/C — Unit Cost

The cost of one move, one day, one TEU-slot, etc. COA maintains two families of unit costs:

  • U/C-CM — cargo-variable unit costs (Node/Link, Agent commission, DEM/DET, EQ Repo, Avg RPB, Slot Internal Pricing). Used to compute CM per booking.
  • U/C-OP — operation unit costs (EQ Holding, General Expense, Port Tariff, Bunker, In-House Hire). Used to compute OP per VVD.

Node / Link

A Node is a point (port, inland depot, customer door). A Link is the movement between two nodes (port-to-port sea leg, CY-to-door trucking leg). All logistics costs in COA are either Node costs (stevedorage, THC) or Link costs (sea freight share, inland haulage).

DEM / DET — Demurrage & Detention

Customer-side charges when a container sits past its free time:

  • Demurrage — container stuck at the port past free time (usually customer hasn't picked up / delivered).
  • Detention — container stuck outside the port past free time (usually at the customer's yard).

Both show up as revenue on your side and as unit-cost inputs in COA's Manage U/C-CM > DEM/DET screen.

MRI / RPB / Slot Internal Pricing

MRI — Master Rate Index
Reference cost index used when a contract rate isn't available, so COA still has a cost to plug in for the accrual.
Avg RPB — Average Revenue Per Box
Used to fill revenue on bookings where no B/L has issued yet.
Slot Internal Pricing
Transfer-pricing rate used when one office sells to another office's booking — the cost of slots "bought internally" from another region.

Offices: Contract vs Loading

Every booking has two office attributes:

  • Contract Office — the office whose customer signed the contract (usually sales origin).
  • Loading Office — the office at the port where the container is loaded.

Reports can be viewed either way. As a Cost Controller you'll typically use Loading View (to tie costs to the operations office that incurred them) and Trade/Sales will use Contract View (to tie revenue to the office that earned it).

What COA actually does

COA is the brain of the cost side of OPUS. It does not generate invoices or payments — that is done in PSO / TES / TRS / JOO. What COA does is turn thousands of individual cost events into one coherent picture of profitability per booking and per voyage.

Three things happen in COA:

  1. You maintain reference data. C/A codes, unit costs (U/C-CM and U/C-OP), port tariffs, bunker rates, EQ holding costs. This is the "cost table" layer.
  2. COA applies the unit costs to each booking and voyage to compute an estimated CM and OP the moment the BKG is created. This is the "estimated performance" layer — your cost accrual.
  3. COA recalculates when actuals arrive (from the invoice modules) and drives the reporting / simulation layer.

High-level business process

  1. Map accounts. Set up the C/A codes and map Logistics / Source account codes to them. This is the once-a-quarter work that quietly breaks all your numbers if it's wrong.
  2. Maintain unit costs. Cargo-variable (U/C-CM) and operation (U/C-OP) unit costs. Keep them current; outdated unit costs = variance against actual.
  3. Create Target VVD & Network Cost. At the start of every cycle, create the voyages you expect to analyse and attach a network cost (the "budget" per voyage).
  4. COA picks up bookings automatically. Each new BKG gets an estimated CM using your unit costs.
  5. Weekly batch recalculates affected BKGs when actuals land (invoices confirmed in PSO/TES/TRS/JOO).
  6. You run the reports — Node Cost, Route Cost, P&L by Lane/VV — to explain variances to management.

COA — Cost Table & C/A Code setup

Home › COA › Cost Table

The Cost Table is the master-data layer of COA. It defines the cost elements that every downstream calculation refers to. Get this wrong and every subsequent COA number is wrong too. Get it right once and it rarely needs touching.

The C/A Code hierarchy

COA has a four-level hierarchy plus three parallel "cost code" views:

LevelNameExample
1Profit LevelSales / Contribution Margin / Operating Profit
2Main GroupingFreight Revenue, Cargo Variable Cost, EQ Fixed Cost, Business Activity Cost, Operation Variable Cost, Operation Fixed Cost
3Sub GroupingTHC Origin, Inland Haul, Stevedorage, Port Charge, Bunker…
4C/A Code (Performance View Code)4-digit code e.g. OTHC (Origin THC)
5Cost ItemLowest leaf — the actual line you'll see in reports

On top of this, three parallel code sets link the C/A Code out to other systems:

  • Performance View Code — what you see in COA reports.
  • SO Cost Code — what TES / TRS use on service orders and invoices.
  • Financial Cost Code — what PSO uses, and what interfaces to the ERP (so this is effectively your mapping to the GL accounts).

Maintaining the mapping between these three is the single most important cost-controller task in COA. A mismatched SO Cost Code will cause the invoice-side amount to post to a different Performance View row than the accrual, producing phantom "variance".

COA — Manage U/C-OP (operation unit costs)

U/C-OP costs are the fixed-ish, per-voyage costs that COA uses to compute Operating Profit at VVD level. Unlike U/C-CM (which flows per booking), these accrue per voyage regardless of cargo.

The per-day cost of holding a container in the fleet: lease / hire, depreciation, repair amortisation. COA uses this × average holding days × TEU count to charge each VVD. Rates vary by EQ size/type and owner type (own, short-term lease, long-term lease, etc.).

General Expense

Lump-sum operation overhead allocated per voyage (office costs, insurance, etc.), usually defined per lane and lane-level TEU basis.

Per-port rate for PSO-related charges (berthing, pilotage, tug, lines, garbage, water). These are a shadow copy of the PSO tariff tables — maintained here for accrual purposes. When PSO processes an actual port invoice, COA recalculates the VVD using actuals and this shadow copy becomes a variance line.

In practice, you maintain the canonical tariff in PSO > Port Tariff Creation and push it to COA through the standard sync. Don't edit here unless a specific port has to use a different accrual basis.

Cost of bunker fuel per tonne per bunker type (IFO 380, VLSFO 0.5%, MGO, LSMGO). Set per region / bunker port because prices differ (e.g. Rotterdam vs Singapore vs Panama). For vessels under time-charter from within the group or chartered-in. Sets the daily hire COA charges the VVD. Driven by the vessel lease master; usually read-only for Cost Controllers.

  2. what it costs to run each VVD (Network Cost), and

Why this module exists

In liner shipping, you almost never sail your own ships full with your own cargo. You share services with other carriers — either as a Vessel Sharing Agreement (VSA), a Slot Purchase Agreement, or as part of a full Alliance. Every month, one carrier owes another for:

  • Your fixed slot entitlement (Slot Hire based on BSA).
  • Slots used above entitlement (Over-Used Slot — OUS — based on TDR/RDR).
  • Special container charges (Reefer / DG / Tank surcharges).
  • Any other bilateral arrangements.

JOO is the OPUS module that accumulates these amounts by carrier × VVD, applies the contractual terms from your BSA master, and produces A/P and A/R CSRs to the ERP.

Settlement options

Each Master Agreement specifies how the settlement is calculated. JOO supports three:

CycleOne specific rotation cycleShort sea / feeder services with named cycles.

  • Reports & TDR/RDR — monthly summaries, TDR / RDR upload and inquiry.

What PSO does

When a vessel berths, a host of port expenses are incurred: berthing, pilotage, tug assistance, mooring, water, garbage, light dues, etc. Each port has its own tariff, sometimes based on GRT (Gross Register Tonnage), sometimes NRT, sometimes LOA (Length Overall), sometimes a mix. PSO is the module that:

  1. Stores the tariff rules for every port your vessels call.
  2. Calculates the expected port charge for each VVD (so COA can accrue).
  3. Processes the actual invoice from the Port Office / Port Agent and audits it against the tariff.
  4. Handles canal transit fees (Suez, Panama) — advance-payment workflow and actual settlement.
  5. Creates CSRs for ERP posting.

Why tariffs are complex

Port tariffs aren't a single rate — they're a ladder of formulas, conditions, and exceptions. PSO supports two construction methods:

Tariff List method
The simplest case. Tariff follows a clean Object × Object Rate matrix, e.g. NRT × rate per NRT. You enter the rates and PSO multiplies. Used by ports with "civil service" tariffs.
Formula Selection method
For complex tariffs that don't fit Object × Rate. You build the tariff as a formula (e.g. IF GRT > 10000 AND LOA > 200 THEN rate_band_A ELSE rate_band_B), using operators and Objects (NRT, GRT, LOA, DWT, etc.) from the Object List.

  • Tariff Simulation — dry-run calculator.
  • Planned Expense & Monthly Estimation — create the voyage-level estimate.
  • Port Charge Invoice Creation — actual invoice audit & confirm.
  • Canal Transit List — Suez / Panama / Kiel transit fees.

  1. Retrieve the S/P invoice. Enter S/P code, invoice number, date. If the S/P already pre-filed the invoice via EDI, PSO has it; otherwise you enter the invoice header manually.

  4. Audit. Accept, adjust, or dispute each line.
  5. Select additional cost items. The Default Setting pre-fills common items; add others as needed.
  6. Save → Confirm. Saving is reversible; Confirming locks it for CSR creation.

How the audit works

Every TES invoice audit follows the same three-tab pattern:

  1. Coincidence — containers where the agreement-based calculation matches the S/P's invoiced amount. These go straight to the Cost Calc. tab.

Storage models: FD vs FP

Free Day (FD)
Each container gets a fixed number of free days in the yard; charges start on day N+1. Most common globally.
Free Pool (FP)
The S/P gives the carrier a pool of container-days per month. Any container-day over that pool is billable. Common at some Asian ODCYs with big carriers.

Data tip: The Storage Dwell and Storage Fee Estimation spreadsheets your team already produces from terminal EDI are essentially the same calculation as TES Off-Dock CY + MR Storage. When TES disagrees with your spreadsheet, usually the free-day count is different because the spreadsheet uses Cargo Available Date and TES uses Move-in Date. Always reconcile on the date definition first.

How accrual works in Allegro — visual map

Home › Workflows › Accrual flow diagram

How to read this diagram. Every coloured box is a real OPUS screen — click it to jump to the wiki entry for that screen. Arrows show the direction of data flow. The diagram is grouped into seven phases that run top-to-bottom over a typical accrual cycle (usually one calendar month per voyage).

What happens in each phase

Phase 1 — Master data setup

Before any accrual can run, someone (usually Finance or MDA) has to load the rate tables. The COA Cost Table is the authoritative rate book. U/C-CM and U/C-OP are summary unit costs the COA uses for quick allocation. The operational modules each have their own rate store: PSO Tariff, TES AGMT, TRS AGMT. JOO Setup holds the partner allocation rules (BSA, TDR, RDR, Financial Affairs).

Phase 2 — Upstream triggers

Accrual doesn't start on its own. It reacts to three events: a new BKG (Booking) comes in from Sales, a VVD (voyage) is confirmed from Vessel Schedule, or a CTM (container move) is posted from Operations. Estimated Cost by VV is the first screen you run once the voyage is set as the target.

Phase 3 — Estimation

COA pulls every booking on the target voyage, multiplies each container by the rate from the cost table, and allocates the result across BKG / Lane / VV (Allocation logic). This produces the Estimated CM and OP — the first profitability view. Critically, this happens before any vendor invoice arrives.

Phase 4 — Actual invoices arrive (50-60 % of your time)

Over the next few weeks, vendor invoices trickle in. Each invoice lands in its home module: PSO Port Charge, PSO Canal, TES MR, TES Off-Dock, TES Storage, TRS Haulage Invoice, TRS USA Rail, and JOO Settlement. Each module does the same thing: retrieve expected amount from its rate store, audit against the vendor invoice, and either accept or push discrepancy back. See Invoice workflow for the full recipe.

Phase 5 — CSR creation & ERP interface

A "Confirmed" invoice isn't yet posted to the GL — it still needs to become a CSR (voucher), get approved, and push to ERP. See CSR → ERP workflow. JOO has an extra step: JOO Monthly Clearance consolidates everything with a single partner into one net settlement.

Phase 6 — COA reconciliation

Every week (sometimes daily), COA runs a batch that pulls every confirmed / posted invoice from PSO, TES, TRS, and JOO back into the BKG-level cost record. The Cost Accrual workflow describes this reconciliation in detail. After the batch: Estimated cost is replaced by Actual cost on the containers that have posted invoices. The remainder stays estimated until those vendors invoice.

Phase 7 — Reporting & simulation

This is where you, as Cost Controller, spend most of your analytical time. The core screens are P&L by Lane / VV / BKG and Cost Simulation. Any big variance (Estimated vs Actual) is a signal: either the rate table is wrong (fix in Phase 1), or the invoice is wrong (push back to vendor), or the upstream data (BKG / VVD / CTM) was incorrect. The feedback loop is the whole point.

Workflow — Monthly Cost Accrual end-to-end

Home › Workflows

This is the walkthrough you'll live every month as a Cost Controller. It stitches together the five cost modules plus COA into one end-to-end close.

Week 1 — preparation

  1. Refresh reference data. In COA:
    • Cost Table — confirm new cost items / C/A codes added last month are mapped to Performance View, SO Cost Code and Financial Cost Code.
    • U/C-CM and U/C-OP — load updated rates: bunker price, port tariff changes, DEM/DET updates, agent commissions.
    • Target VVD — ensure all month's VVDs are in scope. Run Crosscheck COA vs. BKG.
  2. Load new agreements in TES AGMT and TRS AGMT — any newly signed terminal / transport contracts.

Week 2-4 — transactional (day-to-day)

  1. Vendor invoices arrive — process them on the day:
    • Port / Canal → PSO Port Charge Invoice
    • Terminal handling & storage → TES MR, Off-Dock CY, MR Storage
    • Inland transport → TRS Invoice Audit
    • Alliance slot hire / OUS → JOO Settlement (end of month)
  2. Each confirmed invoice becomes a CSR — approve and interface to ERP promptly to avoid month-end backlog.
  3. Monitor COA Weekly Batch — if it fails, investigate the same day.

Month-end close (last 3 working days)

  1. Freeze invoices — target: all PSO, TES, TRS invoices for the month are Confirmed and interfaced by Day-1.
  2. JOO Monthly Clearance:
    1. Verify all target voyages are settled or excluded.
    2. Run Combined Monthly Clearance Creation.
    3. Create A/P and A/R CSRs, get approval, interface.
  3. Run PSO Monthly Estimation — locks the port-charge accrual.
  4. COA final batch — run the final Weekly Batch covering month-end; verify success.
  5. Reports — pull P&L by Lane / P&L by VV, Node Cost, Route Cost, Office Report vs Pre Week.
  6. Accrual vs actual analysis:

    • Document the reason; feed back into U/C table updates for next month.

Workflow — Vendor Invoice Processing

Home › Workflows

Every vendor invoice follows the same five-step flow regardless of which module owns it. The screens differ; the process doesn't.

The five steps

  1. Receive — invoice arrives via EDI, email, S/P portal, or paper. Log it with invoice number, date, amount, currency.
  2. Retrieve the expected amount:
    • PSO retrieves it from the tariff.
    • TES retrieves it from the AGMT.
    • TRS retrieves it from the W/O (which itself came from the agreement).
    • JOO retrieves it from the financial affair × TDR / RDR data.
  3. Audit (match expected vs actual):
    • Coincidence rows → accept.
    • Discrepancy rows → investigate one of (a) S/P error in the invoice, (b) rate not loaded correctly, (c) data issue in BKG/VVD/CTM upstream. Fix the root cause or adjust the line.
  4. Confirm — locks the invoice. From here, you can't edit without cancel-confirm.
  5. Create CSR & interface — the confirmed invoice becomes an A/P CSR, gets approved in OPUS, then pushes to the ERP.

Every module has a CSR I/F Inquiry screen. Use it to see the I/F status per CSR with the error message from ERP when it failed. Typical errors:

After fixing the ERP-side issue, re-queue the CSR for I/F. Don't re-create the CSR — the original one is what the audit trail wants.

FAQ & troubleshooting

Home › Reference

My accrual doesn't match actual — where do I start?

This is the #1 question for Cost Controllers. Systematic approach:

  1. Pull COA → Inquiry by Source Data for the VVD / BKG in question. This shows every invoice that contributed to the actual.
  2. For each, check the cost-code mapping. If the SO Cost Code in TES/TRS maps to a different Performance View Code than the accrual's C/A code, you're comparing apples to pears. Fix in Register C/A Code.
  3. If codes align, compare rates. Likely the U/C-CM / U/C-OP rate is stale vs. the invoice rate.
  4. If rates also align, check units. Usually a different denominator (e.g. actual is per TEU, accrual is per FFE).

I can't find a booking in COA — why?

  • Your Office scope doesn't include that booking's office. Change the Office filter (if you have rights) or request access.
  • The booking's VVD isn't in Target VVD. Add it.
  • The booking was created after the last Weekly Batch. Wait for batch or force a BKG cost recalc.

My CSR is stuck — what now?

Check the I/F Inquiry screen in the owning module. The error message is always one of: vendor not found, GL inactive, cost centre invalid, double posting. Fix on the ERP side and re-queue — don't re-create.

The vendor is disputing my audit — what can I dispute?

TES/TRS/PSO keep a full history of discrepancy reasons. Pull:

  • The AGMT snapshot at the invoice date (TES AGMT → Inquiry → Detail → History).
  • The CTM container move list (vendor often disputes that a move happened).
  • The tariff formula / condition active at the time (PSO → Port Tariff Inquiry).

Someone changed a rate and now ten thousand bookings are wrong

Use BKG Cost Recalculation — scope by VVD / Lane / Period, press Execute. Don't fix bookings one by one.

The "Down Excel" file is too large to open — why?

Pagination isn't applied to exports. Narrow the date range before exporting, or use the Customized Condition inquiry to reduce columns. A Node-Cost export of a full month's data across all lanes can easily hit 100MB.

What if EDI data hasn't arrived from a terminal?

TES audit falls back to manual keying. Enter the invoice header, use Up Excel to upload a container list from the S/P's PDF / Excel. Or wait for the EDI — most terminals settle within 48h of request.

Tips for Cost Controllers

Home › Reference

Reports first, screens second

For anything analytical, start with Multi-Dimension Reports — specifically Inquiry by Customized Condition and Inquiry by Source Data. They give you the answer in one trip; the transactional screens give you one record at a time.

Down Excel is your friend

Every inquiry in OPUS has a Down Excel button. Pull, analyse in Excel, build your dashboards. This both speeds up your reporting and gives you a snapshot you can refer back to six months later without having to hope the system gives the same answer.

Keep a "variance drivers" file

Every month, note the top 3 variance drivers between accrual and actual. After 6 months you'll see patterns — e.g. "Singapore THC always under-accrues by 4%", "USA rail surcharges always over-accrue". Feed these into the U/C tables so next month's accrual is closer.

Never Confirm at the end of the day

Confirm locks the invoice. If you Confirm at 17:30 and realise at 09:00 next morning that the rate was wrong, you'll need Cancel-Confirm + re-audit. Save heavily during the day; Confirm in a single morning session when you're fresh.

Learn the SO Cost Code ↔ Performance View Code mapping

Print out Register C/A Code's SO Cost Code grid and keep it on your desk. 80% of accrual-vs-actual arguments are resolved by consulting this mapping.

Use Simulation before committing anything

COA Simulation and PSO Tariff Simulation are safe sandboxes. If you're unsure whether a U/C change will ripple correctly, simulate it first.

Document your port-charge estimates

PSO's Monthly Estimation is the number you'll be asked to defend. Keep the supporting detail (which tariff rows, which vessel particulars, which omission adjustments) so you can explain variances without re-running the calc.

Monday morning routine (15 mins)

  1. Target VVD → Crosscheck vs BKG — anything missing?
  2. Weekly Batch Monitoring — last run status?
  3. Target Voyage vs Unsettled — any new overdue?
  4. CSR I/F Inquiry (pan across modules) — any failed?
  5. PSO Invoice / TES Invoice / TRS Invoice — what's aged in Saved state?

Build once, re-use forever

The monthly dashboards you build (Storage Dwell, Comparison, etc.) can reuse the same COA / TES / TRS source exports. Design your Excel so changing the month's input file regenerates everything. It pays back in Month 3 when the deadline hits.

When all else fails: Screenshot the screen + error + navigation path and log it with your IT vendor. CyberLogitec has a structured support channel; vague emails get vague answers. Include the VVD / BKG / CSR number every time.
